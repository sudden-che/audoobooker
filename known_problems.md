# Известные проблемы и планируемые обходные решения

## Telegram не отправляет большие аудиофайлы

### Симптом

После успешного синтеза бот показывает ошибку:

```text
Ошибка синтеза: Request Entity Too Large
```

Фактически это может быть не ошибка синтеза, а ошибка отправки уже готового
файла в Telegram.

### Причина

Официальный Telegram Bot API разрешает боту загружать аудиофайлы размером не
более 50 MB. Метод `sendDocument` имеет тот же лимит и не решает проблему.

Документация:

- <https://core.telegram.org/bots/api#sendaudio>
- <https://core.telegram.org/bots/features#local-bot-api>

Сейчас при `MERGE_CHUNKS=true` бот:

1. генерирует отдельные чанки;
2. объединяет их в один файл;
3. объединяет итоговые MP3-чанки;
4. отправляет итоговый файл через `send_audio`.

Размер файла перед отправкой не проверяется. Ответ HTTP 413 библиотека
`python-telegram-bot` представляет как `NetworkError`, поэтому бот повторяет
отправку того же слишком большого файла пять раз. Общий обработчик исключений
затем ошибочно называет проблему «ошибкой синтеза».

Есть дополнительный риск: если конвертация WAV в MP3 завершилась ошибкой,
текущая логика возвращает исходный WAV. Он обычно значительно больше MP3 и
быстрее превышает лимит Telegram.

Уменьшение `CHUNK_SIZE` само по себе не помогает, если `MERGE_CHUNKS=true`:
после склейки размер итогового файла почти не изменится.

### Доступные обходные решения

1. Установить `MERGE_CHUNKS=false` и отправлять чанки отдельно. Это самый
   простой вариант, не требующий публикации файлов в интернете.
2. Разделять готовый результат на части меньше безопасного порога, например
   49 MiB, и отправлять несколько файлов.
3. Использовать собственный Local Bot API server. Он поддерживает загрузку
   файлов до 2000 MB, но добавляет отдельный сервис, хранение и обслуживание.
4. Добавить режим `send_link`: публиковать готовый файл по временной ссылке и
   отправлять эту ссылку пользователю.

## Режим `send_link` / `auto`

### Основная идея

Не следует запускать отдельный веб-сервер для каждого файла и останавливать его
через 15 минут. Это создаёт конфликты портов при нескольких одновременных
задачах и усложняет корректное завершение процессов.

Текущая схема:

- основной FastAPI-сервер продолжает слушать внутренний порт контейнера `8000`
  для web-интерфейса;
- для Telegram-ссылок используется отдельный временный download-сервер на
  `DOWNLOAD_SERVER_PORT`, по умолчанию `43561`;
- для каждого результата создаётся отдельная криптографически случайная ссылка;
- ссылка действует 15 минут;
- download-сервер стартует только после создания ссылки;
- download-сервер останавливается, когда активных ссылок больше нет;
- после истечения срока файл и метаданные удаляются;
- по истёкшей или неизвестной ссылке сервер отвечает `404`.

Пример внешней ссылки:

```text
http://server.example.org:43561/d/7df81b8e68b7425f9b81c87e4bb756ad
```

Токен должен содержать не менее 128 бит случайности. Имя файла, ID пользователя
и токен Telegram-бота нельзя включать в URL.

### Режимы доставки

Предлагаемая переменная:

```text
DELIVERY_MODE=telegram
DELIVERY_MODE=send_link
DELIVERY_MODE=auto
```

- `telegram` — текущее поведение: отправлять файл через Telegram.
- `send_link` — всегда помещать результат во временное хранилище и отправлять
  ссылку.
- `auto` — файлы меньше безопасного порога отправлять через Telegram, большие
  публиковать ссылкой. Это рекомендуемый режим.

Для `auto` нужен порог немного ниже официального лимита:

```text
TELEGRAM_SAFE_UPLOAD_BYTES=51380224
```

Это 49 MiB. Запас исключает пограничные расхождения в трактовке MB и накладные
расходы multipart-запроса.

### Жизненный цикл файла

1. Синтез и конвертация завершаются полностью.
2. Проверяется существование, формат и размер результата.
3. Для доставки ссылкой файл переносится из временной рабочей директории в
   постоянный каталог, например `/app/data/downloads/<token>/`.
4. Рядом атомарно записываются метаданные: исходное безопасное имя, время
   создания и время истечения.
5. Бот отправляет пользователю ссылку и сообщает, что она действует 15 минут.
6. FastAPI отдаёт файл только по точному токену.
7. Фоновая очистка удаляет просроченные файлы. При старте приложения также
   удаляются остатки, срок которых уже истёк.

Перенос в постоянный каталог обязателен: текущая рабочая директория удаляется в
`finally` сразу после обработки запроса ботом.

### Обмен данными между ботом и веб-сервером

В `MODE=both` `entrypoint.sh` запускает веб-сервер и Telegram-бот как два
отдельных Python-процесса. Обычный словарь в памяти FastAPI для регистрации
Telegram-файлов не подходит.

Реестр должен быть доступен обоим процессам. Для первой реализации достаточно:

- общего каталога `/app/data/downloads`;
- случайного токена в имени отдельного подкаталога;
- JSON-файла с метаданными, записываемого через временный файл и атомарный
  `rename`.

Если позднее понадобятся одноразовые ссылки, аудит скачиваний или несколько
контейнеров, реестр следует перенести в SQLite или внешнее хранилище.

### Конфигурация

Предлагаемые переменные окружения:

```text
DELIVERY_MODE=auto
DOWNLOAD_DIR=/app/data/downloads
DOWNLOAD_TTL_SECONDS=900
DOWNLOAD_TTL_MINUTES=15
DOWNLOAD_SERVER_HOST=0.0.0.0
DOWNLOAD_SERVER_PORT=43561
DOWNLOAD_SERVER_IDLE_GRACE_SECONDS=5
PUBLIC_DOWNLOAD_BASE_URL=http://server.example.org:43561
TELEGRAM_SAFE_UPLOAD_BYTES=51380224
```

`PUBLIC_DOWNLOAD_BASE_URL` должен содержать адрес, доступный пользователю, а не
`0.0.0.0`, `localhost` или внутреннее имя Docker-сервиса.

### Docker и порт 43561

Постоянный FastAPI внутри контейнера слушает порт `8000`, но для публичной
Telegram-ссылки используется отдельный временный сервер на `43561`.

```yaml
ports:
  - "127.0.0.1:8000:8000"
  - "0.0.0.0:43561:43561"
```

То есть запрос к `http://<адрес-сервера>:43561` попадёт на временный
download-сервер. Веб-интерфейс на `8000` в compose доступен только локально на
хосте.

Публикация порта Docker не гарантирует доступ из интернета. На сервере также
должны быть настроены firewall, внешний IP или NAT/port forwarding и,
возможно, DNS.

### Безопасность

Публиковать каталог целиком или отдавать путь из query-параметра нельзя.
Endpoint должен принимать только случайный токен и получать реальный путь из
проверенных метаданных.

Минимальные требования:

- запрет directory listing;
- защита от `..`, symlink и path traversal;
- непредсказуемый токен;
- срок действия 15 минут;
- удаление файла после истечения срока;
- корректный `Content-Disposition` с безопасным именем;
- ограничение количества одновременных скачиваний;
- отсутствие токенов и персональных данных в access-логах.

Обычный HTTP не шифрует файл и ссылку. Любой узел между пользователем и
сервером может их перехватить. Для доступа через интернет рекомендуется HTTPS
через reverse proxy или туннель. Если временно используется HTTP, порт следует
открывать только для доверенной сети или ограниченного набора адресов.

### Реализовано

1. Добавлен общий модуль временного файлового хранилища `download_delivery.py`.
2. Добавлен endpoint `GET /d/{token}` с проверкой срока действия.
3. Добавлена очистка просроченных файлов.
4. Добавлены режимы Telegram-доставки `telegram`, `send_link` и `auto`.
5. В `auto` перед отправкой проверяется размер файла.
6. В `auto` ошибка Telegram `Request Entity Too Large` переключает доставку на
   ссылку.
7. HTTP 413 больше не повторяется как временная сетевая ошибка.
8. В Docker Compose добавлены `DOWNLOAD_DIR`, временный порт `43561` и
   `PUBLIC_DOWNLOAD_BASE_URL`.
9. Download-сервер на `43561` стартует только при создании ссылки и
   останавливается после истечения активных ссылок.

### Что ещё стоит проверить вручную

1. Доступность `http://<адрес-сервера>:43561/d/<token>` извне.
2. Firewall/NAT для порта `43561`.
3. Истечение ссылки через 15 минут.
4. Файл больше 50 MB в режиме `DELIVERY_MODE=auto`.
5. Корректность `PUBLIC_DOWNLOAD_BASE_URL` после деплоя через GitHub Actions.
